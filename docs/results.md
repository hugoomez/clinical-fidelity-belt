# Results

**Reproduced on 2026-08-12** against the code in this repository, on CPython
3.14.2 with the versions pinned in [../requirements-lock.txt](../requirements-lock.txt).

Every number in §1 and §2 was regenerated by running the code, not copied from
the original hackathon write-up. Where a number could **not** be regenerated it
is marked and the reason is given. That distinction is the point of this file.

## 1. Belt in lexical mode (the offline default)

Reproduce with:

```bash
python examples/run_demo.py
```

| Report | Decision | Layer 1 checklist | Layer 2 NER recall | Layer 3 entailment | INFLESZ |
|---|---|---|---|---|---|
| Gold (reference humanisation) | **APPROVE** (3/3) | pass | 80.0 % | 38.1 % | 62.5 |
| Adversarial (seeded attenuations) | **REJECT** (1/3) | fail | 48.0 % | 36.4 % | 57.9 |
| Identical text (control) | **APPROVE** (3/3) | pass | 100.0 % | 100.0 % | 38.5 |

Detail on the adversarial failure: 2 attenuated findings, 2 omitted findings, 13
of 25 entities lost. The gate closes on layers 1 and 2 — exactly the layers that
guarantee coverage.

The identical-text control is worth reading carefully: it scores 100 % on both
voting layers and still fails the readability target (38.5 < 55). A verbatim copy
of the technical report is perfectly faithful and useless to a patient. This is
why layer 0 exists, and why it does not vote.

### 1.1 Discrepancy with the original write-up

The technical memoir written during the hackathon (June 2026,
[Memoria_Tecnica_Idonia_Recog.pdf](Memoria_Tecnica_Idonia_Recog.pdf) §6.1)
reports the gold report as **REVIEW (2/3)**, not APPROVE. The per-layer numbers
in that table are identical to the ones above — 80.0 %, 38.1 %, 62.5 — so the
measurement did not change. What changed is the layer 3 threshold:
`nli_min_entailment_rate` is now `0.30`, and 38.1 % clears it, so layer 3 votes
in favour and the verdict moves from 2/3 to 3/3.

The threshold was recalibrated after the memoir was written, and the memoir was
never updated. The code and the test suite (`tests/test_belt.py::test_gold_is_approve`)
agree with each other; the memoir describes an earlier calibration. The threshold
has been left untouched here, and this note exists rather than a silent edit.

**This does not weaken the central finding, but it does relocate its evidence.**
The claim that the lexical belt produces false positives on faithful reports is
no longer demonstrated by the gold report. It is demonstrated by Recog's
production output — see §3.

## 2. Belt in LLM-as-a-Judge mode

> **Not reproduced in this run.** Requires `GOOGLE_API_KEY` and makes billable
> API calls. The table below is carried over from the June 2026 measurement and
> is marked as such. Reproduce with `python scripts/eval_llm_judge.py`.

| Report | Preserved | Simplified | Omitted | Attenuated | Decision |
|---|---|---|---|---|---|
| Recog production | 2 | 5 | 0 | 0 | **PASS** |
| Gold | 3 | 4 | 0 | 0 | **PASS** |
| Adversarial | 2 | 1 | 1 | 3 | **FAIL** |

The judge (Gemini 2.5 Flash) identified all four seeded attacks in the
adversarial report with confidence 1.0 — the ACL tear presented as "stretched",
the meniscal tear as "a fissure that heals on its own", the omitted
chondromalacia, and orthopaedic referral replaced with conservative
physiotherapy — without producing a single false positive on the two valid
reports. Cost per full evaluation: one API call, 2–3 s latency.

The `simplified` column is what makes this work. Five of seven findings in
Recog's output are legitimate simplifications; a system without that category
has to score them as either preserved (missing real attenuations) or altered
(rejecting good reports). The lexical mode has no such category, which is
precisely why it fails on §3.

## 3. The false positive: the belt rejecting a faithful report

> **Not reproduced in this run.** The input file
> `data/reports/knee_mri_recog_production.es.md` — the text Recog returned in
> production — was not preserved. The numbers below are from the June 2026
> measurement. Regenerate the input with `python scripts/fetch_recog_output.py`
> (needs `RECOG_API_KEY`), then re-run `python scripts/eval_recog_output.py`.

| Report | Decision | Layer 1 | Layer 2 NER | Layer 3 entailment | INFLESZ |
|---|---|---|---|---|---|
| Recog production output | **REJECT** | fail | 64.0 % | 28.6 % | 65.3 |

Recog's real output is the most readable of all the reports measured (INFLESZ
65.3, the best score in the set) and it is clinically faithful — the LLM judge
confirms it in §2, with zero omissions and zero attenuations. The lexical belt
rejects it anyway.

This is the project's most useful result, and it is a negative one. The failure
has two distinct causes, and telling them apart was what made it actionable:

1. **Miscalibrated patterns — genuine bugs, fixable by hand.** The MCL
   attenuation pattern fired on *"...without complete tear"*, which is a faithful
   negation, not an attenuation. Fixed with a negative lookbehind so the pattern
   only triggers when the lesion is described as milder than it is.

2. **Inherent limits of lexical matching — not bugs.** String comparison will
   never recognise that *"injury from a blow to the bones"* is equivalent to
   *"bone marrow oedema in a pivot-shift pattern"*. No amount of additional regex
   fixes this; it has to be delegated to a semantic backend.

The dual-backend architecture was designed before this measurement, on the
expectation that lexical matching would hit a ceiling. Hitting it is the
empirical justification for the design, not a defect in it.

## 4. Test suite

```
$ pytest -q
30 passed
```

30 tests, fully offline: no network, no credentials, no model downloads. Coverage
is deliberately uneven and worth stating plainly:

| Covered | Not covered |
|---|---|
| `domain` models and immutability | `IdoniaLiveClient` (needs network) |
| `text_utils`, `readability` | `RecogLiveClient` (needs network) |
| `clinical_checklist`, `clinical_ner` | `clinical_llm_judge` (needs API key, billable) |
| Belt voting, all decision branches | `api/main.py` (no HTTP-level tests) |
| Three-phase pipeline, stub end to end | |

The uncovered modules are exactly the ones that cannot run in a hermetic test
environment. That is a coherent boundary, not an accident, but it does mean the
live clients are verified only by having been exercised by hand.

## 5. Implementation status

**Working and verified:** the four-layer belt, the pipeline in stub mode, the
end-to-end demo, the 30-test suite, the FastAPI application with upstream error
handling, the LLM judge, and Recog humanisation against production.

**Not validated end to end:** Idonia in live mode. The JWT signing and Magic Link
flow are implemented from the staging Swagger and exercised against it, but full
validation depended on activation by Idonia's support team and never happened.
Treat `IdoniaLiveClient` as implemented-but-unconfirmed.
